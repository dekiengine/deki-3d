deki-3d

レンダーパスとして動くソフトウェアラスタライズの 3D：メッシュ、透視投影カメラ、.obj インポート。2D と 1 つのフレームバッファを共有します。

リポジトリ: github.com/dekiengine/deki-3d · 最新リリース: 0.30.0 · エンジン 0.30.0 以降が必要 · 依存: deki-rendering

DekiEditor --packages-add deki-3d <project> か、パッケージマネージャーからインストールします。エンジン自身のコンポーネントと C++ API は Deki のドキュメントにあります。

エディターでは 3D と表示されます。

コンポーネントリファレンス

Mesh3DSettings

How the 3D pass draws: tiles, texture and vertex switches, light and threads.

インスペクターでの名前: Mesh3D 設定 · カテゴリ: 3D · 型: Deki3D::Mesh3DSettings

プロパティ 型 デフォルト 制約 説明
tileSize int32 32 8 から 512 Tile edge in pixels. The depth buffer is one tile, so 32 costs 2 KB and suits a microcontroller, while a desktop can afford 128 or more.
perspectiveCorrect bool true テクスチャの遠近を補正します。オフにすると PlayStation 時代のハードウェアのようなゆがみが出て、塗りのコストが約 1 割減ります。
vertexSnap bool false 投影した頂点を整数ピクセルに丸め、固定小数点時代のハードウェアのような揺れを出します。
lightYaw float -25 -180 から 180 Direction the scene light comes from, swept around the vertical axis. 0 puts it behind the camera, 90 to the right.
lightPitch float 55 -90 から 90 How high the scene light sits. 90 is directly overhead, 0 level with the horizon.
ambient float 0.25 0 から 1 How lit the faces turned away from the light still are. 0 leaves them black, which is dramatic; higher flattens the shading out.
fillThreads int32 1 1 から 16 How many threads fill the screen on a device or simulator build. Tiles are independent, so this is the one part that scales with cores: 1 starts no threads at all, 2 suits a dual-core board, and above the core count it stops helping. The editor always previews with one thread, since it loads packages as unloadable DLLs; the picture is identical either way.

MeshComponent

3D メッシュを描きます。位置はオブジェクトのトランスフォームで決まります。表示するには、シーンのカメラを透視投影にする必要があります。

インスペクターでの名前: メッシュコンポーネント · カテゴリ: 3D · 型: Deki3D::MeshComponent

プロパティ 型 デフォルト 制約 説明
mesh AssetRef (Mesh) "" コンパイル済みのメッシュアセットです。インポートしたモデルをここに割り当てます。空のままにすると、代わりに下のプリミティブを描きます。
primitive enum "Cube" Cube, Quad, Pyramid メッシュアセットが割り当てられていない間に描く組み込みの形です。
tintColor Color "#000000FF" メッシュ自体の色に乗算します。白ならそのままです。
shading enum "VertexLit" Unlit, VertexLit, Flat Unlit is flat colour. Vertex lit shades each vertex against the scene light. Flat shades whole triangles, which is the faceted look.
doubleSided bool false メッシュの外側だけでなく内側も描きます。塗りのコストはおよそ 2 倍になります。

sortingOrder, ignoreClip, pixelSnap, alphaMode を RendererComponent から継承します。

変更履歴

変更履歴は英語です。

0.30.0

Changed

  • minEngine 0.30.0: built against engine 0.30.0. A build of this package from before does not load and is rebuilt.
  • The pass gathers lights only with deki-rendering's lights feature on (DEKI_FEATURE_LIGHTS): a device build with no Light in its scenes leaves Light out, and meshes draw unlit as in a scene without one.

Declares the capabilities it uses

  • package.json has "capabilityDefines": ["opengl"] and "filtersTexturesWith": ["opengl"]: its GL mesh backend tests DEKI_CAPABILITY_OPENGL and samples textures filtered. The editor reads them instead of knowing opengl itself; needs the editor from this release.

The memory check covers hosted targets that state their memory

  • A model is checked against externalMemorySize on any target that states it. A target that provides hosted (an operating system runs the game: a desktop, the Miyoo Mini) used to be skipped whatever it stated, as one that provided desktop-os; it is skipped only when it states no memory, since its memory is then its operating system's.

The software rasteriser draws a model of any size, faster

  • A frame of more triangles than RasterConfig::batchTriangles (8192) is drawn in batches against one depth buffer for the screen, so any mesh draws in fixed memory; a frame within one batch fills tile by tile as before. The triangles and tile lists are in PSRAM where the board has it (RegionArray): as std::vectors they took a board's internal heap and, with Sponza, aborted the T-Deck. With no memory for another batch the frame draws what it has and says so once. The build's memory check counts this working memory (Raster3D::WorkingBytes) beside each model on a board without OpenGL.
  • A part of a mesh out of view is skipped (Submesh3D bounds, worked out when the mesh loads), and a triangle outside the view or facing away is dropped before it is lit.
  • Each vertex is transformed and lit once per part, not once per triangle using it (a 128-vertex cache).
  • Each row of a triangle is filled from where its edges cross the row, not by testing every pixel of its box; setup and the edge walk are 32-bit for a triangle near the screen. The same pixels as before.
  • An RGB565 framebuffer with a flat, palette or RGB565 texture has a loop of its own (FillSpan565): the span's settings in registers, and its shading and cutout chosen once per span rather than tested per pixel. The same pixels; on a T-Deck a full screen of textured 3D fills about 8 ms sooner.
  • An ARGB8888 framebuffer (the Miyoo Mini's, a desktop's in software) with a flat colour or an RGB565, RGB888 or RGBA8888 texture has one too (FillSpan8888): the same structure, a pixel kept as its red and blue and its green so a grey light shades it with two multiplies, and a flat colour shaded once a span. The same pixels as the generic loop, which the new RasterSpans test checks against an RGB888 framebuffer for every texture kind, shading, cutout and depth setting (and in the big-endian build). On a desktop a 640x480 frame of lit cubes at 128-pixel tiles fills in 0.50 ms untextured (from 0.93), 1.07 with an RGB888 texture (from 1.41), 1.09 with RGB565 (from 1.44) and 1.19 with a cut-out RGBA8888 one (from 1.43) (RasterSpans.DISABLED_Argb8888FillSpeed). A palette, RGB565A8 or ALPHA8 texture still takes the generic loop.
  • A triangle's span settings and the loop that fills its spans are set once per triangle, not per span, and a span's step comes from a table of reciprocals. The same pixels.
  • Each vertex is projected once, in the vertex cache: a triangle wholly in front of the near plane is binned from its corners' projections without the clip's copies, and the early backface test reads them instead of dividing six times. The same pixels.
  • A binned triangle keeps its colour and light once, its first corner's, the only ones the fill reads: 92 bytes, not 124, written to PSRAM once and read back once a tile. The same pixels.
  • On an Xtensa FPU (ESP32-S3) that divide, and a triangle's 1/area, are the FPU's reciprocal estimate and two Newton steps, inline, where a divide is a library call: within an ulp, and the T-Deck's corridor frames come out pixel for pixel the same.
  • A row of a triangle is bounded by two of its edges, not three: above its middle corner by the two from the top corner, below by the two to the bottom one (the same pixels). Its spans step from the row's values at x = 0, with u and v already in texels and z in depth units, so a span keeps four bases and four steps, which the FPU holds, instead of reading the whole gradients back from the stack. Depth can round an ulp differently, which settles a tie between two surfaces at the same depth the other way: about 0.5% of Sponza's pixels, in the distance.
  • One divide per span finds the w at both its ends (a divide is a library call on a microcontroller's FPU). w can differ by an ulp, which moves a texel only where its edge falls within about a millionth of a texel of a pixel's centre.
  • The frame's clear is drawn by the rasteriser, under each tile as its first fill reaches it (Raster3D::SetBackground, from QuadBlit::TakePendingClear), rather than over the whole screen first; a frame lit the same all over gets it lit (deki-rendering). Otherwise the clear is made before a mesh can write (QuadBlit::BeforeWriting).
  • fillThreads 2 fills on the second core of an ESP32-S3: the fill worker is pinned to the core the engine is not on (it ran on the same one). deki-3d now needs ESP-IDF's pthread component.
  • fillThreads above 1 shares out the geometry too (transform, lighting, clipping, projection) for a part of a mesh of 256 triangles or more: each thread takes blocks of 256 triangles in turn, into its own vertex cache and triangle list, and the calling thread bins them in their order, so the picture, the batches and RasterStats are the same on any number of threads. The memory is reserved on the calling thread first, since Deki::Memory's tracking is not thread-safe, and a board's worker gets a 4 KB stack for the clip and lighting. More than 16 threads (RasterConfig::kMaxThreads) are held to 16, with a warning. On a T-Deck (ESP32-S3, two cores) the 2k-triangle corridor's geometry drops from 11.8 ms to about 9.6; on a Miyoo Mini (two Cortex-A7s) the 13k-triangle island scene runs at a steady 30 frames a second.
  • RasterStats counts batches, triangles dropped, parts skipped, and the time spent on geometry and on filling.
  • Sponza (Detail 10%, which keeps 82k triangles, one directional and one ambient light) on a LilyGO T-Deck: 1 frame a second, from a reboot loop. Now 1.3. A textured corridor of 2,000 triangles at 320x240: 20.4 frames a second (21.1 unlit), from 11; of 1,000, 26.7, from 14 (drawn in strips, the frame in PSRAM).
  • DISABLED_DrawACompiledMesh (by hand) draws a compiled mesh file, or an .obj at a Detail, as a T-Deck does (320x240 RGB565, one and two threads), to compare a board's picture with the desktop's.
  • The tile size is the platform's unless the scene fixes one: the new Mesh3DSettings.tiles is Platform (the default) or Fixed, and Fixed uses tileSize everywhere. A platform names its own with DEKI_3D_TILE_SIZE=<n> in its platform file's defines; one that names none gets 32, which a microcontroller's internal RAM holds. The Miyoo Mini (deki-miyoo-boards) names 64, which beat 32 there (a 6k-triangle scene from 52.8 to 56.6 frames a second in RGB565, 58.0 to 59.7 in ARGB8888), and the desktop simulator (deki-desktop-integration) 128; the editor previews at
    1. The inspector shows each target's, and the build's memory check counts a target's own. A scene saved before, which had one size for every platform, takes the platform's if it kept the old default of 32 and stays Fixed at any other size (a scene migration). The picture is the same at any size.

Fewer divisions on a 32-bit core

  • A row's covered span is found without 64-bit divisions: where the edge values are 64-bit, a short shift-and-subtract finds the pixel count, which never exceeds the tile's width. On the Miyoo Mini (built for the Cortex-A7, whose hardware divide the compiler now uses) software division went from 8 to 12% of the CPU to 0.1%, and the 2k-triangle island from 11.8 to 11.1 ms of render a frame; on the T-Deck the 2k corridor from 43.0 to 42.7 ms.

Models at any size, built for each platform

  • A mesh of any size compiles: 16-bit indices up to 65535 vertices, 32-bit past that (Mesh3D::indexBytes, Mesh3D::IndexAt). Both renderers draw either. Mesh files are version 5 (the header ends in flags); version 4 files still load.
  • Each platform's build keeps what it can use. A model's own setting is Detail, per platform: the share of triangles kept (editor/MeshSimplify.h: edge collapse by quadric error, never moving a seam, an open edge or a material border, never turning a triangle over).
  • A model's textures follow their images' own settings for the platform: Format, Max Size and Filter (Point, Bilinear, Trilinear; Texture3D::filter, from the engine's TextureFilter), set in the image's inspector, several at once. There is no cap of the model's own: a board's build says when a model does not fit. On the GPU Bilinear is linear, and Trilinear linear between mipmaps; the software rasteriser draws Point. MeshCompileOptions::textureFor gives each texture's settings by its image's path.
  • What a model is compiled from (ObjSourceFiles: its material library and images) is part of its cache stamp, so a change to one rebuilds it.
  • The Model inspector (.obj): what the editor's build holds, and the Targets cards for Detail, Default and per platform. Settings in editor/ModelSettings.h; a model's .data from before, with texture settings of its own, loses them when saved.
  • A board build stops when a model needs more external memory than the board has, naming its images' Max Size and its Detail, and warns when Detail stops above what it asks.
  • A mesh loads from its file part by part, each straight into its own buffer (MeshAsset::LoadFromFile), so loading takes the mesh's size in memory. The loader read the whole file in first and then copied it, so a load held twice the mesh (8.6 MB for a 4.3 MB one), and a mesh the build check let through could still not load on the board.
  • The importer reads map_d as a texture's cutout and paths written with backslashes. CompileObjToMesh takes a MeshCompileOptions (each texture's settings, detail, and a report of what it did) in place of its last two arguments.
  • Breaking: Mesh3D::indices is a const void* read through IndexAt.
  • Tests: BigMeshTests.cpp, MeshSimplifyTests.cpp, the GPU drawing past 65535 vertices, bilinear and trilinear textures, and an off-centre shadow, which the centred cube test could not catch a mirrored lookup with. By hand: DISABLED_CompileAModel and DISABLED_AModelUnderTheSun take a real model (DEKI_TEST_OBJ).

Lights and shadows

  • Meshes are lit by the scene's DekiRendering::Light components: an ambient colour and up to 8 directional, point and spot lights, in colour, by distance, cone and facing, up to twice a colour (LightAt, Light3D, RasterConfig::lights). The software rasteriser lights a mesh by the 4 lights that reach it most and shades per channel.
  • Shadows on the GPU, from up to two directional or spot lights a frame (ShadowMap, Mesh3DBackend::DrawShadowCaster), cast by every mesh with the new MeshComponent::castShadows (on by default). The software rasteriser draws without them and says so.
  • A scene without a Light draws its lit meshes unlit and says so once per mesh; a lit mesh LightsItself(), so the 2D light goes under it.
  • Breaking: Mesh3DSettings loses lightYaw, lightPitch and ambient; a scene saved with them opens with an Ambient and a Directional Light that light it as before. RasterConfig::lightDirection and ambient (a float) become ambient (a colour) and lights. DrawMesh takes the model matrix, Identity by default.
  • Breaking, for shaders: Fragment.light is a float3, one light per channel; Fragment.position (world space) and LightAt(position, normal) are new. uLightDir is gone.
  • Ortho in Math3D.h.

Added

  • Mesh3DBackend: what draws the pass's meshes. Raster3D is one; GLMesh3DBackend draws them on the GPU, through OpenGL ES 3.0 or desktop OpenGL 3.3, where the platform provides opengl (DEKI_CAPABILITY_OPENGL). A board without it compiles none of it. RasterConfig and RasterStats moved to its header (Raster3D.h still includes it).
  • Mesh3DSettings.renderer: Auto (the GPU where the platform has OpenGL), Software or GPU.
  • MeshComponent.shader, shaderParams and shaderColor, and the same on Material3D: a GPU shader for the mesh (deki-rendering's ShaderAsset), in HLSL with Displace() and Shade() hooks (editor/MeshShaderUse.cpp, which the built-in program is generated from too). The software rasteriser draws the shading model and warns once.
  • Mesh3DSettings.composeOnGpu and RasterConfig::composeOnGpu: a GPU backend may draw straight into a frame the display builds on the GPU, leaving the CPU buffer with only the 2D drawn after the meshes. On by default; off for a scene that reads the whole frame back.
  • Mesh3D::revision and Texture3D::revision, which change with the data so a GPU backend can keep its uploads. Mesh assets and the built-in primitives set them (NextRevision()).
  • Mesh3DBackend::WritesBuffer: whether a batch reached the frame through the buffer. Where the 2D is drawn on the GPU too (deki-rendering's QuadBlit::BlitSink), Mesh3DPass tells it after a batch that did (the software rasteriser, a GPU backend reading back), so the meshes stay between the 2D drawn before and after them. The pass itself says it writes nothing (RenderPass::WritesBuffer).

Fixed

  • Tint colours were packed in the wrong byte order (ToRGBA8888 where materials keep 0xAABBGGRR), so any tint but white came out with its channels swapped. With the default tint, opaque black, that turned every mesh red. The default is now white, as its tooltip always said; a scene that saved the old default now draws its meshes black, as it asks.
  • Big-endian boards (DEKI_RGB565_BIG_ENDIAN): RGB565 into an RGB565 framebuffer came out byte-swapped, while every other framebuffer format was right. Meshes now hold RGB565 and RGB565A8 textures in memory's byte order once loaded, as images do, and the rasteriser reads and writes 565 values in that order. Nothing changes on little-endian boards.
